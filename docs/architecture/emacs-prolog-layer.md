# Embedded Emacs Prolog layer

Mara vendors its Emacs-to-Prolog integration in the repository instead of
requiring a separate Emacs package or starting a fresh `swipl` process for every
query.

## Components

```text
emacs/mara-prolog.el
        |
        | newline-delimited JSON over stdin/stdout
        v
prolog/mara-prolog-server.pl
        |
        +--> prolog/mara-memory.pl
```

`mara-prolog.el` is the process/runtime library. It knows how to start, stop,
restart, synchronously call, and asynchronously call a persistent SWI-Prolog
child process. It does not know Mara's memory predicates.

`mara-prolog-server.pl` is the narrow server boundary. It decodes one JSON
request per line, dispatches only registered internal methods, and emits exactly
one JSON response per line. Prolog stderr is kept off the protocol stream.

`mara-brain.el` is the Mara-specific client. It owns one runtime instance,
synchronizes `memory.json` when Mara's memory revision changes, and exposes
relationship/retrieval operations to the rest of Mara.

## Elisp API

Create a runtime:

```elisp
(setq runtime (mara-prolog-make-runtime))
```

Lifecycle:

```elisp
(mara-prolog-start runtime)
(mara-prolog-live-p runtime)
(mara-prolog-restart runtime)
(mara-prolog-stop runtime)
```

Synchronous request:

```elisp
(mara-prolog-call runtime "ping")
;; => ((status . "pong"))
```

Asynchronous request:

```elisp
(mara-prolog-call-async
 runtime
 "ping"
 nil
 (lambda (result error-value)
   ...))
```

Callbacks receive `(RESULT ERROR)`. Request IDs are generated by the Elisp
runtime and responses are matched to pending calls, so later Prolog methods can
complete out of order without changing the caller API.

## Protocol

Request:

```json
{"id":1,"method":"relevant","params":{"query":"editor"}}
```

Success:

```json
{"id":1,"ok":true,"result":{"memories":[]}}
```

Failure:

```json
{"id":1,"ok":false,"error":"..."}
```

The transport deliberately does **not** expose arbitrary Prolog `call/1` or a
model-facing eval endpoint. New operations are added as explicit server methods.
This keeps model text and retrieved memory from becoming executable Prolog.

## Mara brain lifecycle

Normal Mara code does not call the transport directly. Use:

```elisp
(mara-brain-start)
(mara-brain-restart)
(mara-brain-stop)
```

`mara-brain-relationship-snapshot` and `mara-brain-relevant-memories` lazily
start the process if necessary.

Before a Mara-specific query, the brain compares its loaded-memory stamp with
current state. The stamp includes:

- the `memory.json` path
- Mara's in-process memory revision
- file size
- file modification time

A new Prolog process always forces a reload because its dynamic fact database is
empty even if the JSON file did not change.

## Failure behavior

If the subprocess exits, outstanding requests are failed and the runtime is
marked stopped. A later Mara brain call starts a fresh process and reloads
memory before querying it.

Synchronous requests have a bounded timeout. The process is not a network
service and opens no listening socket.
